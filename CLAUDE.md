# Project guidelines

## Project description

Bedrock-based WordPress starter, meant to be kept as a reference baseline for future projects. It must stay minimal: add only what is strictly needed, one piece at a time.

- **Stack:** WordPress via [Bedrock](https://roots.io/bedrock/) (Composer-managed), Timber (Twig templates), Secure Custom Fields (optional, not installed yet).
- **Theme:** `web/app/themes/base`, a minimal Timber theme.
  - `functions.php` initializes Timber and sets `views` as the Twig directory.
  - `page.php` / `index.php` build the context and render `views/page.twig` / `views/index.twig`.
  - `views/base.twig` is the base layout (includes `partials/header.twig` and `partials/footer.twig`).
  - Pages render the content of existing WordPress pages (`post.title`, `post.content`).
- **Local environment:** configuration in `.env` (not committed; use `.env.example` as a template). Default URL: `http://x-wordpress.test`.
- **Deployment:** from Git. Only code and configuration are committed; dependencies, uploads and generated files are not.

## Language

All code in this project must be written in English:

- function, class, variable and hook names
- code comments and docblocks
- user-facing strings (theme output, labels, admin texts)
- documentation, commit messages and file headers

## Translations and admin language

- The admin (backend) language is **English (United States)**, which needs no language files. Only one admin language is used at a time.
- `web/app/languages/` contains generated language packs (`.mo`, `.po`, `.l10n.php` and hashed `.json` files). They are **not committed** (ignored in `.gitignore`, only `.gitkeep` is tracked). They can be deleted safely and are regenerated by WordPress.
- Frontend multilingual content (if needed) is handled by a translation plugin (e.g. Polylang or WPML), not by core language packs. Theme strings are translated with `.po`/`.mo` files placed in `web/app/themes/base/languages`, and those **are committed**.

### Changing the admin language

Run these commands (locally and as a step of the deployment, since language files are not in Git):

```bash
wp language core install it_IT
wp site switch-language it_IT
wp language plugin update --all
```

It can also be changed from WP admin: Settings → General → Site Language. Replace `it_IT` with the desired locale. To go back to the default, switch to `en_US`.

## Blocks and field groups

- Content is built only with custom Secure Custom Fields blocks, one folder per block in `web/app/themes/base/blocks/<name>/`:
  - `block.json` defines the block (name `acf/<name>`),
  - `fields.php` defines its field group in PHP with `acf_add_local_field_group()`,
  - `render.php` renders the Twig template `views/blocks/<name>.twig`.
- Blocks are registered automatically by `functions.php`, and the allowed block list is built from the `block.json` files. Core blocks, patterns, the block directory and Openverse are disabled.
- Current blocks: `wysiwyg` (a single WYSIWYG field with a minimal toolbar and no media upload).
- **SCF Local JSON is NOT enabled.** Field groups are defined in PHP only, so they do not appear in the Field Groups admin screen and cannot be edited from the admin UI. Do not create field groups from the admin UI.
- To change a block's fields (e.g. add a caption to a carousel), edit the block's `fields.php` and its Twig template, then commit. Keep field keys unique and stable.
- Header and footer are fixed in code (`views/partials/`) and are never editable by the client.
